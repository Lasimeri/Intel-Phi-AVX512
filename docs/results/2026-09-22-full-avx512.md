# 2026-09-22 (night): the full AVX-512 instruction set, and llama.cpp

## What was asked

An unmodified llama.cpp, built by its own CMake for AVX-512 (which
enables F, CD, VL, DQ and BW), run on the host with its AVX-512
executed by the card. Nothing patched in llama.cpp; the co-processor
is what changes. The first attempt died on its very first AVX-512
instruction, `vinserti64x2 ymm1, ymm1, xmm0, 1`: a 256-bit form, which
the translator refused because the card is 512-bit only. A census of
the build: 15,377 of its 25,184 EVEX instructions are 128-bit or
256-bit forms, and it uses byte and word lanes, scalar conversions,
divides, permutes and mask instructions the card has no equivalent for.

## What was built

The translator (`host/crates/avx512-xlate/src/rewrite.md`) now
expresses every such form as a sequence on the card: narrow forms
under lane masks with the upper lanes zeroed, zeroing masks, memory
operands staged through the alignment-free unpack pair, scalar forms,
general-register moves, inserts, extracts, block shuffles, ternary
logic, conversions (float16, float to int with the integer indefinite,
integer to float through x87), 64-bit lane shifts, min and max with
AVX-512's NaN rule, all thirty-two compare predicates, the VEX mask
instructions, division and square root by Newton-Raphson from the
card's estimates, scaling, rounding, and the permutes composed from
`vpermd`. The sequences keep what they clobber in a per-thread scratch
area on the card reached through `fs`, not on the program's stack
(which the threads of a split loop share); the worker publishes its
displacement (`VPU_OFF_SCRATCH`).

Four defects surfaced by the new test (`tools/avx512-narrow-test.md`):
the qword pack-store needing 8-byte alignment where AVX-512 needs none,
a `vmovq` into rax lost to the restore order, a chunk kept mapped and
writable from a ranges-mode region giving a later demand-mode region
stale reads and lost writes (fixed in `card/vpu/vpu_exec.c`), and the
planner keeping the dense flag on a merge of a read range into a
written one, so the phase read the card's stale pages of that range
(`plan.md`).

The worker is now cross-built on the host (`scripts/phi-vpu.sh
deploy`: three files in parallel, linked statically, 0.4 s) instead of
on the card (minutes), with another card as the fallback.

## Measured (card 0)

| check | result |
| --- | --- |
| `tools/avx512-narrow-test.c`, 66 forms against plain C | PASS, bit-exact |
| `scripts/phi512-ground.sh` | all three agree to the bit |
| `tools/avx512-seamless-test.c` 65536 (regression) | 7.8 ms polynomial, all bit-identical |

llama.cpp, `build-avx512` (its own flags), Qwen2.5-0.5B, card 0:

| run | outcome |
| --- | --- |
| `llama-simple`, F16, default 4 threads | 19 regions, then the program spins on the host: the region is ggml's OpenMP barrier, whose counter the other host threads change under the card's snapshot (the documented concurrency limit, met in practice) |
| `llama-simple`, Q4_0, 4 threads | 1,140,632 regions in 600 s, no refusal, no wrong result, still repacking weights when the timeout hit |
| `llama-bench -t 1 -p 4 -n 2`, F16 | each refusal fixed in turn: `vpcmpneqb` before `kortestq`, `vcvtps2pd`, a 4-byte `kortestb` followed by a branch, `vpermi2ps`, `vcvtusi2sd`, `vrndscalesd`, `vscalefps`, `vdivps`; then 1,933,828 regions in 1078 s (about 1,800 regions per second) with no refusal and no wrong result, until the program crashed on the host after a one-instruction region (not yet understood; the ranges-mode hole below is the suspect) |

The per-region cost is 0.5 ms: three mailbox round trips through the
window, the bundle DMA, the fetch and the write-back. llama.cpp's
regions are a handful of instructions each (its 512-bit code is
interleaved with 256-bit VEX code the host runs itself, and every VEX
instruction ends a region), so a token needs millions of them. The
translator is no longer the limit; the region floor is, and it is
three orders of magnitude away from usable. The conclusion of the
afternoon stands: llama.cpp needs the card as a ggml backend (one
matmul per request, weights resident), which `GGML_BACKEND_PATH` loads
into an unmodified build.

## Not done

Byte and word lane arithmetic (`vpmaddwd`, `vpshufb`, `vpaddw`,
`vpackuswb`, ...) and 64-bit masks in general: the card's lanes are 32
bits and its masks 16 bits, so these need dword synthesis and a
representation for wide masks. Gathers and scatters, embedded rounding
on register operands, `vshufpd` with a different selection per block.
The RANGES-mode soundness hole (an undeclared access inside a mapped
chunk) is still open.
